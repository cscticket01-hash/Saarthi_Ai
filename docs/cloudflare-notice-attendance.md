# Cloudflare first, school Drive eventually

Only notice records and the mobile attendance outbox move to Cloudflare. School identity, entitlement checks, Firebase Auth, QR authorization, other school collections and existing Drive file storage remain on their existing paths. Android background push still uses the existing FCM transport; Cloudflare stores notices and attendance, not the Android operating system's push transport.

The Cloudflare Worker uses SQLite Durable Objects: 256 deterministic attendance lanes per school, one notice journal per school and one background Drive coordinator per school. Attendance ingestion does not serialize through the school coordinator. New Android clients receive a broker-issued, school/session/QR-bound capability and submit approved attendance directly to Cloudflare; their attendance does not wait behind Render's general request limit or an Apps Script lock. A grant lasts no longer than the existing 15-minute attendance approval. Expired capabilities renew through the authenticated broker. Issued-card enforcement deployments retain the broker path until equivalent edge reader verification exists; final Drive delivery always rechecks entitlement and reader/capture authorization.

Cloudflare SQLite commits precede accepted receipts. Accepted is not completed: attendance is completed only after the existing signed school Script returns a matched receipt. The local mobile SQLite outbox remains durable through retries. On cutover, older Firestore queue entries continue draining and status checks fall back to legacy receipts if no Cloudflare entry exists. The same deterministic operation IDs prevent duplicate final attendance.

Notices import their current verified Drive baseline before the first Cloudflare write. Cloudflare then owns notice revisions, tombstones and compare-and-swap decisions. Existing Windows delta/point reads and mobile notice lists read the Cloudflare view. Each accepted notice retains an ordered durable Drive intent. Its predecessor's final Drive revision is resolved before delivery; later edits cannot overtake a retry. External Drive conflicts retain the Cloudflare intent for school review instead of overwriting external changes. Other Drive-backed data follows the existing sync engine.

Background delivery is coordinated per school and spread across schools. A coordinator processes one lane at a time and retains backoff across new arrivals. It uses the existing <=25 attendance operation Script batches, exact receipt matching and lease fencing. No pending intent expires simply because a retry or process restart occurred. Cloudflare unavailable responses preserve the original client operation rather than silently writing a competing Firebase copy.

## Configuration and rollout

Worker: `vidya-saarthi-sync.vidya-saarthi-cscticket01.workers.dev`. SQLite binding and migration are declared in `cloudflare-sync/wrangler.jsonc`. The shared transport key is a Cloudflare secret, not a source/config value, and is also configured on the broker as `SAARTHI_CF_SYNC_KEY`. The broker URL is `SAARTHI_CF_SYNC_URL`; `SAARTHI_CF_SYNC_SCHOOLS` is a comma-separated verified school allowlist, or `*` for all managed schools. Without both endpoint/key the old behavior remains. A configured endpoint/key with an empty school list activates no school. Keys never enter the app, logs, repository or reports.

Do not turn off Cloudflare while it has uncommitted notice or attendance work. That would hide its newer notice revisions and outstanding receipts behind an older Drive snapshot. Drain/resolve work and reconcile every school before any rollback. Updating Worker code must retain its Durable Object class, namespace and migration history.

## Evidence and capacity

`npm ci --ignore-scripts`, `npm run types`, `npm run check`, `npm run build`, `npm test` run from `cloudflare-sync`. Copy `.dev.vars.example` to `.dev.vars` only for local type generation/tests. `test/runtime.test.mjs` executes real local workerd SQLite storage, authenticated transport, revision races, replay/claim fencing, encryption, scoped direct mobile grants and the broker's actual notice routing.

`node scripts/load-attendance.mjs` submits up to 100,000 **synthetic local** mobile requests to workerd, with a mocked unavailable Drive destination. It reports accepted/failed requests, concurrency and latency percentiles. This is not a live Cloudflare throughput or end-to-end Drive benchmark. Production capacity still requires a paid-tier/quota check and a controlled live test with realistic active device concurrency. Do not advertise 100,000 simultaneous requests or a completion time from a local run. Cloudflare receipt time, device visibility and eventual Drive backlog are distinct metrics.

Measured local run (2026-10-28): 100,000 synthetic students, 256 concurrent requests, 100,000 accepted, zero failures, 191.03 seconds total; median 135 ms, p95 293 ms, p99 14.24 seconds. The long tail matters: this is not evidence of 100,000 devices completing in one second. Raw summary: `docs/cloudflare-attendance-local-load.json`.
